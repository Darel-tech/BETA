# Architectural Decision Record (ADR): Embedding Quantization in pgvector

## Status
Accepted

## Context
The BETA knowledge store indexes 384-dimensional dense vectors generated by `sentence-transformers/all-MiniLM-L6-v2`. At scale, uncompressed 32-bit floating point vectors require:
$$384 \times 4\text{ bytes} = 1,536\text{ bytes per vector}$$
Excluding indexes, $10^6$ vectors require $\approx 1.54\text{ GB}$ of RAM/storage. Including an HNSW graph ($O(M)$ connections per layer), memory consumption nearly doubles.

We investigated three quantization strategies to achieve the target of up to $4\times$ smaller storage with negligible accuracy loss:
1. **Approach A: `halfvec` (16-bit Float / FP16)**
   - *Storage*: $384 \times 2 = 768$ bytes ($2\times$ reduction vs float32).
   - *Pros*: Native in pgvector 0.7.0+, zero application quantization overhead, minimal precision loss ($<0.1\%$ difference in cosine ranking).
   - *Cons*: Yields only $2\times$ reduction rather than the $4\times$ goal.
2. **Approach B: `int8` Scalar Quantization with Per-Vector Scale & Re-ranking**
   - *Storage*: $384 \times 1\text{ byte} = 384$ bytes + 4 bytes scale float = 388 bytes ($\approx 3.96\times$ reduction, matching the $\approx 4\times$ target).
   - *Mechanism*: Map float range $[-1.0, 1.0]$ to signed 8-bit integers $[-128, 127]$ using affine/symmetric scalar quantization ($q_i = \text{round}(v_i / \text{scale})$). Store int8 vectors in binary / bytea or compact column with exact dot product / cosine similarity, followed by rescore/re-rank on top candidate pool.
   - *Pros*: High compression ($\approx 4\times$), fast computation, high recall@10 ($>97\%$) on normalized embeddings.
3. **Approach C: Binary Quantization (`bit(384)`) + Exact Re-ranking**
   - *Storage*: $384 / 8 = 48$ bytes ($32\times$ reduction).
   - *Mechanism*: Convert positive signs to 1, negative signs to 0 ($1\text{ bit per dimension}$). Compare via Hamming distance (`<~>` operator in pgvector), then retrieve candidate pool ($2\times k$ or $3\times k$) and re-rank against float32/int8 embeddings.
   - *Pros*: Extreme compression ($32\times$), lightning-fast XOR/POPCNT SIMD distance.
   - *Cons*: Greater loss of directional granularity for fine-grained ranking without a re-ranking stage.

## Decision
We implement a pluggable `Quantizer` protocol in `services/retrieval/app/adapters/quantizer.py` supporting:
- `none` (Float32 passthrough baseline)
- `int8` (Symmetric int8 scalar quantization with per-vector scale factor, achieving $\approx 4\times$ memory reduction)
- `binary` (1-bit binary sign thresholding with candidate re-ranking)

The active mode is governed by `QUANTIZATION_MODE` in `config.py` (default: `none` / `int8` configurable).
All memory and recall differences are empirically measured and verified via `scripts/benchmark_storage.py`.
